# Add i18n Support (English / Korean)

- **날짜**: 2026-02-14
- **이슈**: https://github.com/foxyberry/quant-investment/issues/34
- **브랜치**: `feature/i18n`
- **상태**: 계획중

## 목표

웹 프론트엔드에 next-intl 기반 다국어(영어/한국어) 인프라를 구축하고, 레이아웃 및 대시보드 페이지를 번역하여 동작하는 i18n 시스템을 완성한다.

## 배경

현재 웹 UI의 모든 텍스트가 영어로 하드코딩되어 있다. 한국 주식(KOSPI) 사용자를 위해 한국어 지원이 필요하며, 추후 다른 언어 확장이 용이한 구조를 갖추어야 한다.

**현재 상태:**
- Next.js 16.1.6 + React 19 + Tailwind 4
- i18n 라이브러리 없음, proxy.ts/middleware.ts 없음
- 하드코딩된 영어 문자열이 40+ 컴포넌트에 분포

**기술 선택: next-intl 4.x**
- Next.js App Router 네이티브 지원
- Server Component + Client Component 모두 지원
- `[locale]` 라우팅 + proxy.ts 기반 locale 감지
- 주간 다운로드 93만+ (de facto standard)

## 계획

- [ ] 1단계: next-intl 설치 및 i18n 인프라 구축
  - `next-intl` 패키지 설치
  - `src/i18n/routing.ts` — locale 정의 (en, ko, default: en)
  - `src/i18n/request.ts` — 서버 요청별 locale/messages 로드
  - `src/i18n/navigation.ts` — Link, useRouter 래퍼 (locale 인식)
  - `src/proxy.ts` — locale 감지 미들웨어 (Next.js 16)
  - `next.config.ts` — next-intl 플러그인 적용
- [ ] 2단계: 라우트 구조 변경 (`[locale]` 세그먼트)
  - `src/app/layout.tsx` → 최소 root layout (html, body만)
  - `src/app/[locale]/layout.tsx` → 기존 RootLayout 이동 + NextIntlClientProvider
  - 모든 페이지를 `src/app/[locale]/` 하위로 이동
- [ ] 3단계: 번역 메시지 파일 생성
  - `messages/en.json` — 영어 메시지 (네임스페이스별 구조)
  - `messages/ko.json` — 한국어 번역
  - 네임스페이스: common, nav, dashboard, screening, portfolio, strategy, analysis, backtest
- [ ] 4단계: 레이아웃 컴포넌트 번역 적용
  - Header.tsx — useTranslations('nav')
  - Sidebar.tsx — useTranslations('nav')
  - Footer.tsx — useTranslations('common')
- [ ] 5단계: 대시보드 페이지 번역 적용
  - page.tsx + 대시보드 위젯 4개 컴포넌트
- [ ] 6단계: 언어 전환기(Language Switcher) 추가
  - Header에 EN/KO 토글 버튼 추가
  - locale 변경 시 URL 자동 전환 (/en/... ↔ /ko/...)
- [ ] 7단계: 검증
  - 빌드 성공 확인
  - 영어/한국어 전환 동작 확인
  - 기존 기능 정상 동작 확인

## 기술적 고려사항

- **Next.js 16**: `middleware.ts` → `proxy.ts` 리네임 필수
- **next-intl 4.x**: `NextIntlClientProvider` 필수, ESM-only
- **라우트 변경**: 모든 페이지가 `/[locale]/` 하위로 이동하므로 `<Link>` 컴포넌트를 next-intl의 `createNavigation` 래퍼로 교체 필요
- **Server Component**: next-intl의 서버 컴포넌트용 `getTranslations`와 클라이언트 컴포넌트용 `useTranslations` 구분 필요
- **기존 기능**: 하드코딩 문자열을 메시지 키로 바꾸는 작업이므로 기능에 영향 없음
